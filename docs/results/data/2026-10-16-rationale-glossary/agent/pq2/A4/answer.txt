RATIONALE-APPROVED

The limit is rule R29: "A signed-in user may make 120 requests per clock minute (fixed windows starting at second 0); the 121st and later requests in that minute answer 429 with code `rate_limited` and a `Retry-After` header giving the seconds until the window ends, and write nothing."

The owner approved a rationale for this rule. Its status is current, not stale.

- **Why:** rationale:R29 says "FIXTURE: one signed-in client must not starve the API for everyone else." The limit stops a single client from using up capacity that other users need.
- **Trade-off:** rationale:R29 also says "FIXTURE: a sync burst can hit 429 and must retry after the window." A client that sends a burst of sync requests may be refused with 429 and has to wait for the window to end.

The rationale explains why a per-user cap exists. It does not say why the number is 120 rather than some other value, and nothing recorded explains that choice.

Related rule R30 says a sync or batch request counts as one request, whatever it contains. It has no recorded rationale.

I changed nothing.
